## STEP 2: 更新タイミングとデータ基準日

### 2-1 関係するワークフロー
| ワークフロー | 起動条件 | 処理 | 書き込み先 |
|---|---|---|---|
| `Macro_Data_Update.yml` | cron `0 10 * * *`（毎日UTC10:00）・手動 | `common/macro_data/fetcher.py --start <400日前>`でFRED 25系列を取得 | `common/macro_data/series/`・`macro_data_violations_log.json` |
| `MACRO_PULSE_Update.yml` 日次 | cron `15 22 * * *` | `05_main.py --date $(date -u +%Y-%m-%d)`（events・流動性・meta）＋`--remind` | `docs/market-monitor/macro-pulse/data/` |
| 同 fill-returns | cron `3 13 * * *` | `05_main.py --fill-returns`（S&P500のt+1/5/10/20を後から補完。画面では使わない） | 同上（`05_events.csv`） |
| 同 update-schedule | cron `7 22 * * 6`（土曜） | `--update-schedule`（予定表＋FED context。REGIMEの再判定は月の最初の実行だけ） | `05_indicator_schedule.csv`・`05_fed_context.csv` |
| 同 weekly-analysis | cron `11 22 * * 6`（土曜、2026-05-27に日曜から変更） | `--weekly-analysis`（スコア・AI解説・サプライズ） | `05_weekly_analysis.csv` |

- `workflow_run`による連鎖は無い。`Macro_Data_Update`（UTC10:00）→`MACRO_PULSE_Update`日次（UTC22:15）の順は、
  時刻差（12時間）だけで保たれている。実績（下表）では前者が13:30〜17:49、後者が翌00:09〜01:58に起動し、
  間隔は最短6.3時間あった（順序が逆転した回は無い）。
- Market Data Daily・Market Pulseとの連鎖は無い（MACRO PULSEは`common/market_data/daily/`を読まない）。共有はFRED系列ストアのみ。
- 他に`common/macro_data/`・MACRO PULSEの出力に書くものは手動スクリプトだけ（`05_import_history.py`・`05_backfill_nfp_mom.py`・
  `migrate_bamlh0a0hym2_history.py`）。
- 日次の起動が毎回UTCの0時をまたいでいるため、`--date $(date -u +%Y-%m-%d)`は**予定日の翌日**になる（直近20回すべて）。
  流動性CSVの行の日付は予定日の翌日になり、`run()`の「今日発表予定の指標」の照合（`schedule.release_date == date_str`）は
  1日先の予定と照合される（実例: Michigan Inflation 1Yの`2026-09-25`の枠に、9/25の確報の発表〈米国東部10:00〉より前の
  00:35 UTCに、FREDにあった7月分〈4.2〉が書かれた）。

### 2-5 月次・週次の指標の並べ方
- **日付の置き方（混在）**: `05_events.csv`の`release_date`は、指標によって観測日と発表予定日が混ざっている。
  2026-04-01以降の行で数えると、Philly Fed 6/6・CFNAI 5/5・Sahm 6/6は観測日（月初1日）、Initial Claimsは観測日（週末の土曜）12行と
  予定の枠6行、Building Permitsは観測日4行と予定の枠6行、Michiganは観測日1行と予定の枠5行。予定の枠に入るかどうかは
  `refresh_monthly_indicators()`が「観測日＋`obs_to_release_lag`±14日」の範囲に未使用の枠を見つけたかで決まる。
  Initial Claimsは本来週次だが、events.csvには2026-04-01以降18行しかない（同じ期間のFREDの観測は26週）。
- **前方埋め**: スコア・カード・ヘルスバーは「今日以前の最後の行」を使う（ステップ状に引き延ばす）。古さはカードのtooltipの
  「観測日」でだけ分かる（ただしMichigan・Building Permitsは予定の枠の日付が出る、N-09）。流動性CSVは日次の行に、週次・月次系列の最新値を
  毎日書き写す（`fred_latest()`は保存済みの最新値を返すため、コードのコメントにある「非公表日はNone」は起きない）。カードの日付は
  行の日付（実行日のUTC日付）で、観測日は出ない（N-12。注記「値は次回発表まで変わりません」で一般論としてだけ開示）。
- **過去のスコアの先読み**:
  - 画面の比較バー・スコア推移（`computeScoreAsOf()`）は`updated_at <= 対象日`で、その時点で未取得の行を除く（MACRO-BUG-1）。
    日次の実行が書いた行には有効。ただし2026-03-28/29に一括で取り込んだ過去分（33,727行）の`updated_at`が取り込み日のため、
    2026-03-29より前の日付では全指標が「未取得」になり、スコアがnullになる（B-03）。
  - レーダーとスライダーの正規化値（`l3LatestBefore()`）は`updated_at`を見ない（先読みあり）。スライダーの横のスコアは
    `computeScoreAsOf()`で先読み除外ありのため、同じスナップショットで両者の前提が違う（MM-11）。
  - AIカードの「週±・月±」と、Grokに渡す「先週比・前月比・週差・月差」（`_compute_score_change()`・`_compute_current_score()`）は
    `release_date`だけで絞るため先読みが入る。観測日（月初）で置かれた月次指標は、発表週の「1週間前」の時点にも既に入って
    いることになり、週の変化が0になる。直近12週の`score_change_1w`は12週すべて0（実際の週次スコアは08-15→08-22で27→22、
    08-30→09-05で22→27と変わっている）。09-20の行ではPhilly Fedが09-17に47.4→37.8へ変わったのに「週差+0.00」（B-05）。
  - 改定値: events.csvは最初に書いた値を上書きしないため、過去の時点の再現としては正しいが、「今」の値も改定前のまま

### 2-7 取得の遅れ・欠けた実行の原因
- 欠けた実行: 直近20回（cronごと）で、予定があったのに実行が作られなかった回は0。遅れは日次+1.9〜3.7h、fill-returns +3.3〜7.0h、
  Macro Data +3.5〜7.8h、週次+0.4〜2.4h（GitHubのscheduleの遅れ）。
- Initial Claims: `INDICATOR_CONFIG["Initial Claims 4W MA"]["fred_release_id"]=321`は「Empire State Manufacturing Survey」
  （毎月15日ごろ）で、Initial Claims（IC4WSA）の公表元は180「Unemployment Insurance Weekly Claims Report」（FRED API
  `fred/series/release`・`fred/release`で確認）。このため予定表のClaimsの枠が月1回（毎月15日ごろ）になり、
  `refresh_monthly_indicators()`が最新週の値を次の15日の枠へ書く。その行は枠の日付まで「未来」なので、今日の計算に入らない（B-01）。
- YC・RRP・S&P500の1営業日の遅れ: Macro Dataの取得が1日1回・米国の引け前（実績13〜17時UTC）で、当日分はFREDの公表が

- REGIME: 月に1回だけ再判定する設計（`record_month`、B-07）。
- Michigan: 取得元（FRED）の掲載が約1か月遅れ。Macro Dataのログでも09-10時点のUMCSENTは675件（8月分なし）で、
  ストアに8月分が入ったのは09-26の取得から（09-25のFREDの更新後）。
- 週末・祝日: 日次のcronは毎日動き、週末は前日と同じ値を書く（流動性CSVの行は週末も作られ、Hollow Rallyの「5日」は暦日）。
